# 0023. Browser notifications use web push

- **Status:** Proposed

## Context

[OG-89](https://linear.app/offgridos/issue/OG-89/generic-notification-core-with-pluggable-channels) adds a browser channel to the notifications core. The architecture handoff names two options: web push and the Notification API.

Web push delivers a message through the push service of the browser vendor (Google, Mozilla, Apple) even when no tab is open. The server makes an outbound call to that service for each message, which the no-outbound-calls rule in CLAUDE.md forbids in local mode. The Notification API needs no outbound call, but it only shows a notification from an open tab, so a person who is away from the page never sees it.

The person chose web push. It is the only option that reaches a person whose browser is closed, and mobile push later uses the same kind of path.

Web push has these constraints:

- The browser gives the server a subscription, which holds a push endpoint and the keys to encrypt to that browser. The endpoint is on the vendor's domain.
- The message is encrypted end to end (RFC 8291). The vendor sees the endpoint, the time, and the size of each message, but not its text.
- The server signs each request with VAPID keys (an ECDSA P-256 key pair).
- Browsers accept push only from a secure context, so the page is served over the local HTTPS that Caddy provides.

## Decision

- We will use web push for the browser channel. The web app registers a service worker and asks the person for notification permission. It subscribes only when the permission is `granted`.
- We will send a push only to a subscription that the signed-in person created on one of their own devices. The channel is off until the person subscribes.
- The payload is the notification message and nothing else. It is encrypted to the subscription keys, and the server never logs it.
- The VAPID key pair is generated by the `init` service into `data/secrets` and loaded as a Docker secret. The server fails fast when the browser channel is enabled and the key is missing. No key goes in the repository or in environment defaults.
- A push endpoint that answers `404` or `410` is removed. Other failures follow the event-bus retry rules: three attempts, then the dead-letter queue.
- This record is an exception to the no-outbound-calls rule in CLAUDE.md. The exception covers only web push to endpoints that a person subscribed. The rule in CLAUDE.md, [.claude/rules/security-privacy.md](../../.claude/rules/security-privacy.md), and [docs/privacy.md](../privacy.md) are amended in the same change. Mobile push is a later channel and needs its own record.

## Consequences

- Easier: a notification reaches a person whose browser is closed, and it uses the same channel interface that mobile push will use.
- Harder: the browser vendor learns when a person's device gets a notification, and how big it is. The privacy statement says so.
- Harder: web push needs HTTPS and a service worker, so the local HTTP-only access that [ADR 0015](0015-no-reverse-proxy-cors-on-the-server.md) describes does not work for this channel.
- Harder: the VAPID key is a new secret that `init` must create and back up, and losing it means every subscription must be made again.
- Follow-up: [OG-90](https://linear.app/offgridos/issue/OG-90) (event reminders) uses this channel. Mobile push needs its own decision record.
