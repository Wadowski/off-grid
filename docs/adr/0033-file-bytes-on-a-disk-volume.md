# 0033. File bytes live on a disk volume behind a storage port

- **Status:** Proposed

## Context

The files module will hold user files: photos, documents and attachments that people add to notes, events and lists. Each file has two parts. The bytes can be large, up to 20 GB or more. The metadata (owner, family, the user-chosen name, content type, size, checksum) is small and must follow the same access rules as the rest of the data in Postgres ([ADR 0009](0009-table-ownership-scopes.md), [ADR 0021](0021-family-membership.md), [ADR 0029](0029-event-guest-access.md)). The files access model, drives, trash and immutable versions are decided in [ADR 0034](0034-files-access-model-trash-and-versions.md). This ADR decides only where the bytes live.

Offgrid runs on small home hardware, including a Raspberry Pi, as a Docker Compose stack. The local deployment runs one server instance ([ADR 0019](0019-state-shared-between-instances.md)). Keeping bytes out of the database keeps the Postgres dump small and fast to write and restore.

Two options were considered for the bytes. Storing them in Postgres large objects would put every file into the database dump and slow backups on slow disks. Running an object store such as MinIO would add a sixth service to the install and needs a lot of memory and disk for a household. Neither is needed for local mode.

The names and paths a user picks are personal data. If they reached the disk, they would leak through the file system and backups, and a user-chosen path could escape the storage folder.

## Decision

We will store file bytes in a folder on the host, `data/files`, bind-mounted into the server container at the same path. The files module owns this folder and no other module reads it. The volume is added when the files module is scaffolded (OG-106).

We will use opaque storage keys. Each key is a random identifier, generated by the server, and the path on disk is derived only from that key (for example `data/files/ab/cd/<key>`). The server writes to a temporary name in the same folder, then renames the file into place, so a partial write is never visible under its final key. User-chosen names, content types and paths never reach the disk. The user-chosen name lives in Postgres, in the files module's own schema, and in file events for consumers under [ADR 0034](0034-files-access-model-trash-and-versions.md). It never reaches the disk or the logs. Input for names and content types is validated with zod at the API boundary ([security and privacy rules](../../.claude/rules/security-privacy.md)).

The files module defines a storage port inside its application layer, with four operations:

- `put`: takes a stream of bytes and returns the storage key, the size in bytes and the SHA-256 of the content.
- `get`: returns a stream of bytes for a key, optionally for a byte range, so that video and large downloads can resume.
- `delete`: removes the bytes for a key. A missing key is not an error. Versions can refer to the same bytes: a restore creates a new version that points at the old bytes ([ADR 0034](0034-files-access-model-trash-and-versions.md), rule 7). So the files module calls `delete` only when no `files.file_version` row still refers to the key. In practice this happens when a trashed subtree is purged. The order is fixed: commit the database delete of the rows first, then check for remaining references, then delete the bytes. A restore that adds a version to the same key after the check is safe, because the check runs after the commit and a referenced key is never deleted. A crash between the commit and the byte delete leaves orphan bytes, which the integrity sweep reports (OG-109). The purge worker runs this check under the files module's own role, so RLS does not hide references.
- `exists`: reports whether bytes for a key are present.

The disk adapter implements the port in the files module's infrastructure layer. Other modules never call the port. They get file facts through versioned events and `packages/contracts` ([ADR 0002](0002-outbox-events-and-projections.md), [ADR 0013](0013-projections-for-other-modules-only.md)).

We will record the size and SHA-256 at write time, on the `files.file_version` row that refers to the bytes. Reads check the size, and an integrity check can compare the checksum against the bytes on disk.

Events follow [ADR 0034](0034-files-access-model-trash-and-versions.md), rule 9: they carry ids, the `sourceVersion`, the drive id and the name, and never file contents. This ADR adds one limit: storage keys, paths and bytes never go into events, because no other module uses the port. [ADR 0011](0011-restricted-event-access-and-retention.md) sets the retention and access rules for events, and [events.md](../../.claude/rules/events.md) applies to the payloads.

### Fit with ADR 0019

Local mode is one server instance with a local disk, and that is the only mode this ADR covers. Metadata and any shared state stay in Postgres, as [ADR 0019](0019-state-shared-between-instances.md) requires. A hosted or multi-instance deployment must not share a plain local disk. It uses another adapter for the same port, an S3-compatible object store, which needs its own decision and an ADR of its own, because it is an outbound network call outside local mode.

### Backup and restore

A backup is two parts taken as a pair: the `pg_dump` of the database and a copy of `data/files`. The two must be taken from the same quiet point, or the metadata can point at bytes that are missing, or bytes can exist with no metadata. The README backup section and [privacy.md](../privacy.md) state this. A restore puts back both parts. The README and privacy.md already describe `data/files` in the backup steps, with the wording "once the files module ships". To get the quiet point, the owner stops only the server before taking the dump and the copy, keeps the database running for `pg_dump`, then starts the server again. The copy of `data/` holds the secrets and the file bytes together, so it is stored with the same care as the dump.

Orphan bytes (no metadata) and missing bytes (metadata without a file) are the expected failure modes of a bad pair. An integrity sweep that reports both is follow-up work for OG-109 or later.

### Export

The `export` module does not call the storage port, and it does not copy the `data/files` folder, because the folder layout uses opaque keys. Instead, the export module asks the files module for an export of its bytes through a versioned event defined in `packages/contracts`. The files module reads the bytes through its own port, pairs them with the user-chosen names from its own Postgres schema, and writes them into the export. The event carries an export request id and never the bytes. The files module writes the bytes into an export folder under `data/files`, which it creates and owns. The export module receives only a reference to that folder through a versioned event, never a path it has to guess. The files module deletes the folder when the export finishes or fails, so the personal data in it does not outlive the export. The exact event names are defined by the export work, with the new-event process. Export is never feature-gated ([CLAUDE.md](../../CLAUDE.md) non-negotiables).

### Privacy

File bytes are personal data on the host. They are not secrets, but they are as sensitive as the database. The folder is readable by the host account in the same way as `data/secrets/`, and the README already asks the owner to lock down that account. The SHA-256 and size are file metadata. They are stored only on the version row, never logged, and never put in events, because a content hash can confirm that someone holds a known file. Neither file contents nor file names are logged ([ADR 0034](0034-files-access-model-trash-and-versions.md), rule 9), and no outbound call is made to store or serve them in local mode. Because names travel in events, every event consumer holds personal data and is bound by the access rules in ADR 0034.

## Rejected options

- **Postgres large objects.** Every file goes into the database dump, so backups grow with the files and become slow on slow disks such as a Raspberry Pi. Large objects also make byte-range reads and streaming harder to keep fast at 20 GB and above.
- **MinIO or another object store in the local stack.** It adds a sixth service to the install, with its own credentials, ports and memory use, which the household install does not need. The storage port leaves room for an S3-compatible adapter in a hosted deployment without this cost in local mode.
- **User-chosen names or paths on disk.** This allows path traversal, leaks names through the file system and backups, and ties the disk layout to user input.

## Consequences

- Backups now have two parts that must be taken together, and the README and privacy statement say so. Restores need both parts.
- Backup size grows with the files, while the dump stays small.
- Streaming and byte-range reads are possible on the disk adapter without loading a file into memory.
- The files module must keep metadata and bytes consistent on write and delete. Follow-up work: the disk adapter and an integrity sweep (OG-109), the module scaffold, volume and config (OG-106), and the S3-compatible adapter for a hosted deployment, with its own ADR.
- Export asks the files module for the bytes through an event, which costs more than a folder copy but keeps names out of the disk layout and keeps the module boundary.
- Purging a trashed subtree (ADR 0034) releases bytes only when no version row refers to them. The purge worker needs this check, and the integrity sweep reports any bytes left behind.
- Restores and cross-owner moves can refer to or copy bytes, so storage grows with use until quotas exist (ADR 0034).
- This ADR sets the direction only. The port and adapter are not built yet, so the status stays Proposed until OG-109 implements it.
