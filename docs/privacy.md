# Privacy statement

This page says, in plain language, what the local Offgrid server does with your data and what it does not do. The technical checks behind these statements are described in [privacy-guards.md](privacy-guards.md).

## What it does not do

- **Nothing leaves the machine at runtime, with four exceptions.** The server and the web app run on your own host. Once the stack is running, it makes no outbound network calls, except in these cases:
  - **Outgoing mail.** If you turn on outgoing mail, the server sends mail only to the mail server that you configure, such as Gmail, iCloud, Fastmail or a server on your own network. Mail is off by default, and the mail content goes to that provider.
  - **Web push.** If you subscribe a browser to web push, the server sends each notification to the push service of that browser's vendor (Google, Mozilla or Apple). The message is encrypted, but the vendor learns when a notification is sent and roughly how large it is. Web push is off until you subscribe, and you can unsubscribe at any time.
  - **Updates.** When an admin checks for or installs an update, or when the admin has turned on the nightly automatic update (off by default, 03:30 in the time zone set by `TZ`), the updater contacts these hosts and no others:
    - `api.github.com`: the release list and the release manifest lookup.
    - `release-assets.githubusercontent.com`: the release manifest file, through a redirect from `api.github.com`.
    - `ghcr.io`: the image manifests of the new release.
    - `pkg-containers.githubusercontent.com`: the host to which `ghcr.io` redirects the image downloads.

    The request carries no personal data. GitHub sees your host's IP address and the time of the request. The server does not contact GitHub itself. It asks the updater container over the internal Compose network, authenticated with a bearer token, and only the updater makes these calls. The nightly on or off setting travels from the server to the updater over that internal network, which is not outbound.

  - **Install.** The install script, which the owner runs once as root on a Linux host, downloads its release files from `github.com` (`docker-compose.production.yml`, `production.env.example`, `SHA256SUMS` and `install.sh`), which redirects each download to `release-assets.githubusercontent.com`, and pulls the images from `ghcr.io`. When Docker is missing, it also downloads the Docker repository key from `download.docker.com`, installs Docker from that repository, and installs the base packages from the distribution's package mirrors. The owner's helper `infra/compose/set-latest-version.sh` calls `api.github.com` once to read the latest release tag, when the owner runs it. The server never runs either. The install-time calls happen only when the owner runs them.

  The first build of the repository (for developers) needs internet access to pull base images and install npm packages.

- **No telemetry.** There are no analytics, tracking or crash-reporting SDKs, and no usage data is collected. `pnpm check:no-telemetry` runs in CI and fails the build if one is added. It scans for known packages and hosts only; the no-usage-data rule is a project policy that review enforces.
- **No accounts with third parties.** Offgrid does not sign you in with an outside identity provider, and it does not need an account with anyone to run.

Sign-in is planned to send traffic over plain HTTP on your local network. Anyone on the same network segment can read passwords and session tokens in that traffic. See [ADR 0016](adr/0016-local-authentication-model.md) for the decision and its trade-offs.

## Sign-in is not built yet

The shipped server has no sign-in. The identity module is an empty stub, so every request is anonymous. User-scoped routes refuse such requests with `UNAUTHENTICATED`. This means the server does not yet separate one user's data from another's on a real request. Until sign-in exists, treat the instance as a single-user installation on a network you trust.

## What it stores, and where

The production stack (the install script or the paste-in Compose file) keeps its data in named Docker volumes. Docker names them `offgrid_<volume>`, with the Compose project name `offgrid` as the prefix. The developer stack from the repository keeps files and secrets in the repository's `data/` folder.

Everything stays on the machine that runs the stack. The `data/` folder, `infra/compose/.env` and the install folder's `.env` are not committed to the repository.

The secrets are readable by anyone who can read the Docker volume directory, which only root can do by default, and by anyone who can read the `data/secrets/` folder of the developer stack. Keep the host account locked down. The update backups hold the same secrets in plain text, including `mail-encryption-key`, so copying a backup copies the key with the data.

Project rules forbid logging personal data or secrets, including in error messages ([security and privacy rules](../.claude/rules/security-privacy.md)). The logger redacts fields whose names contain sensitive words. It does not redact free text in messages, so the rule relies on code review as well. Logs go to the container output.

## Who can reach it

The web app (port 8080 by default) and the API (port 3000 by default) listen on all network interfaces, so other devices on your local network can reach them. The updater publishes no port: its API is reachable only on the internal Compose network and needs a bearer token. CORS settings in `OFFGRID_CORS_ORIGINS` only tell browsers which origins may read responses. They are not an access control, and they do not stop other clients. Anyone on your network who can reach the API can send it requests, so keep the network trusted. See [ADR 0015](adr/0015-no-reverse-proxy-cors-on-the-server.md).

Local access uses plain HTTP, so traffic on your local network is not encrypted.

## Backing up and exporting

- **Back up** the production stack with the commands in the [README, Backup and restore](../README.md#backup-and-restore). The database dump holds your data. The copy of the secrets holds your keys. Store both somewhere safe, outside the host's Docker volumes and off the host where you can. The update backups in `offgrid_offgrid-backups` hold the same secrets, so keep them as safe as the secrets.
- **Back up** the developer stack with the commands in the [README, Develop](../README.md#develop) section. The database dump holds your data. The copy of `data/` holds your secrets. Once the files module ships, `data/files` holds the file bytes and is part of the same copy. Take the dump and the copy while the server is stopped (the database keeps running for the dump), so that the file names in the database match the bytes on disk.
- **Export** as a feature, for example to a file you can read, is planned in the `export` module. It is not built yet. Until it is, the database dump is the way to get your data out. Once the files module ships, the export includes the file bytes, provided by the files module, not by copying the file folder. File names also travel in events, so other modules that keep a copy of them, in the same database, hold those names too.
- **Delete** the production stack by running `docker compose -f docker-compose.production.yml down -v` in the install folder. This removes every Docker volume of the stack: the database, the secrets, the uploaded files, the update backups and the updater status. Then delete the install folder and any manual backup folders, such as `$HOME/offgrid-backup`. This cannot be undone.
- **Delete** the developer stack by running `docker compose -f infra/compose/docker-compose.yml down -v`, which removes the database volume. Then delete `data/` to remove the secrets and, once the files module ships, the file bytes in `data/files`.

## What is not yet in place

- Sign-in and per-user access on real requests (see above).
- Encryption of the data at rest and of local traffic is not in place yet.
