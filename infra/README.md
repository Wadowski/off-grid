# infra

Deployment assets: `compose/` (Docker Compose), `init/` (first-run setup) and `install/` (the install script for Linux hosts).
Not a pnpm workspace.

There are two Compose files:

| File                                    | Images                     | Use                                                                                                            |
| --------------------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `compose/docker-compose.production.yml` | Release images from GHCR   | Production install on a host. The install steps are in the [README, Install](../README.md#install).            |
| `compose/docker-compose.yml`            | Built from this repository | Developer use. Keeps its data in the repository's `data/` folder. See [README, Develop](../README.md#develop). |

The `updater` service (`apps/updater`) runs in both Compose files. The `server` reads the updater URL and token file (`OFFGRID_UPDATER_URL`, `OFFGRID_UPDATER_TOKEN_FILE`) from the same Compose network. The updater has no published port, joins the default network so that `server` and `web` can be reached for health probes, and mounts `/var/run/docker.sock` (or `OFFGRID_DOCKER_SOCKET_PATH`) as the only service with the socket. Set `OFFGRID_DOCKER_GID` to the group id of that socket so the non-root updater can use it (default `0`), and `OFFGRID_RELEASE_REPOSITORY` to the `owner/name` of the GitHub repository that publishes releases (the production Compose file defaults it to `Wadowski/off-grid`; the base file has no default, so the updater refuses to start there until it is set). `scripts/check-compose-no-published-ports.mjs` (`pnpm check:compose`) fails when the updater publishes a port or another service mounts the socket.

## Production Compose file

`compose/docker-compose.production.yml` runs the published release images (`ghcr.io/<owner>/offgrid-main-server`, `offgrid-main-web` and `offgrid-updater`) instead of building from source. It is self-contained, so it can be copied to a host on its own. It needs Docker Compose 2.23 or newer for `configs` with `content`.

- Set up: copy `compose/production.env.example` to an env file, then run `compose/set-latest-version.sh --env-file <path>`. The script makes one call to `https://api.github.com/repos/<OFFGRID_RELEASE_REPOSITORY>/releases/latest`, reads the tag and writes `OFFGRID_VERSION=<version>` into the file. Only the owner runs it, never the server; it needs `curl` on the host and fails without writing when no release exists yet. It is the same class of owner-triggered GitHub call as the update check in ADR 0032.
- Start: `docker compose --env-file <path> -f compose/docker-compose.production.yml up -d`. Without `OFFGRID_VERSION` the file fails fast. The `latest` tag is never used.
- Warning: `OFFGRID_VERSION` goes stale after an in-app update, because the updater replaces the server and web images by digest and does not edit the file. Running `up` with an older value would downgrade the containers while the database is already migrated. Set the value to the installed version by hand before `up`, or re-run the install script, which corrects a stale pin (see Install script). The [README, Updating](../README.md#updating) section has the same warning for admins.
- Volumes: `offgrid-db`, `offgrid-secrets` (generated by `secrets-init`), `offgrid-files`, `offgrid-backups` and `offgrid-updater-state`. Docker names them `offgrid_<volume>`, with the project name `offgrid` as the prefix. The only bind mount is the Docker socket on `updater`, which publishes no port.
- The `configs` block is generated from `init/sql/*` and `compose/secrets-init.sh`. After changing either, run `pnpm compose:production:generate`. `pnpm check:compose` fails when the committed file differs from the generated output.
- The server reads the updater URL (`http://updater:3100`) and the bearer token from the `updater-token` secret file. The token is generated by `secrets-init`. The server holds it so it can ask the updater to check and apply releases; the updater remains the only service with the Docker socket.
- The release images must be public on GHCR, or the pulls need credentials.
- Docker Desktop (macOS and Windows) is not tested. The socket path and group id may need `OFFGRID_DOCKER_SOCKET_PATH` and `OFFGRID_DOCKER_GID`. See [README, Install](../README.md#option-2-paste-in-compose-file).

## Install folder layout

The install script and the paste-in path both use one folder on the host, `/opt/offgrid` by default (the script takes another absolute path from `OFFGRID_INSTALL_DIR`):

- `.env`: the settings, including `OFFGRID_VERSION`. Created once, mode `0600`, and never overwritten by the script.
- `docker-compose.production.yml`: the production Compose file of the installed release.
- `production.env.example`: the template of the release that was installed.

The folder holds no secrets. Secrets live in the `offgrid-secrets` volume. Docker `compose` reads `.env` from the folder automatically, so `docker compose -f docker-compose.production.yml <command>` run in the folder works on the production stack.

## Install script (Linux)

`install/install.sh` prepares a Linux host for the production Compose file. Run it as root on the host, not in the server or in local mode. It checks that the user is root, the CPU is `amd64` or `arm64`, the OS is RHEL, CentOS, Fedora, Debian or Ubuntu, at least 2 GB is free in `/opt/offgrid` (override with an absolute `OFFGRID_INSTALL_DIR`), and that `docker` and `docker compose` 2.23 or newer work. When Docker is missing, it installs Docker Engine and the Compose plugin from the official Docker repository. The repository key is downloaded from `download.docker.com` and its fingerprint is compared with the pinned Docker fingerprint before the repository is added. This download is an owner-run, one-time host setup step; the server never makes it.

Then it installs the stack. The release is `OFFGRID_VERSION` (`X.Y.Z`, a leading `v` is allowed) when that is set. Otherwise it is the version pinned in `.env` from an earlier run, or else the latest release of `OFFGRID_RELEASE_REPOSITORY` (default `Wadowski/off-grid`). It downloads `docker-compose.production.yml`, `production.env.example` and `SHA256SUMS` from that release over HTTPS and checks the two files against `SHA256SUMS`. A mismatch or a missing entry stops the script before anything is installed. It creates `.env` from `production.env.example`, pinned to that version, only when `.env` does not exist. It never creates, reads or regenerates secrets: `secrets-init` writes them into the `offgrid-secrets` volume on first start and never overwrites them. It then runs `docker compose pull` and `docker compose up -d --wait` with project name `offgrid`, waiting up to 300 seconds. On a timeout it prints the `docker compose ps` and `docker compose logs` commands to look at the stack and leaves the stack as it is. At the end it prints the address to open, `http://<host>:<OFFGRID_WEB_PORT>`, and the step to create the admin account.

From the release, the script downloads `install.sh` as an asset next to `SHA256SUMS`, and `SHA256SUMS` lists it. The release workflow (`.github/workflows/release.yml`) attaches `install.sh` from the next release tag onward. Releases before that tag do not have the asset.

Re-running is safe. With the same version it pulls and restarts nothing and keeps `.env` and the secrets. A higher version updates the pin, pulls and restarts. A version lower than the installed one is refused, because a downgrade can break a migrated database. When the pin in `.env` is older than the installed version, for example after an in-app update, the script changes only the `OFFGRID_VERSION` line to the installed version and does not pull or restart.

`OFFGRID_RELEASE_DOWNLOAD_BASE_URL` (https, default `https://github.com`) replaces the download host of the install script. It exists for the end-to-end suite and is not needed on a normal host.

The checksums come from the same GitHub release as the files. They catch corrupted or swapped downloads. They do not protect against a compromised release, because the release manifest and checksums are not signed yet, see [ADR 0032](../docs/adr/0032-outbound-update-check-and-image-pull.md).

The script never changes group membership. When the user who ran `sudo` is not in the `docker` group, it prints the `usermod -aG docker <user>` command for the owner to run.

Supported systems are RHEL, CentOS Stream, Fedora, Debian and Ubuntu. Rocky Linux and AlmaLinux are not supported: on those systems, install Docker by hand and use the paste-in path in the production Compose section above. Other Debian derivatives, such as Kali, are refused unless their release is Debian bookworm, trixie or bullseye, because Docker publishes no repository for other releases.

On a host, run the script as root with `sudo sh infra/install/install.sh` from a checkout, or use the release `install.sh` as described in the [README, Install](../README.md#option-1-install-script-linux).

Manual test of the Docker install branch in containers (needs Docker on the machine running it):

```bash
for image in debian:12 fedora:41 quay.io/centos/centos:stream9; do
  docker run --rm -v "$PWD:/src:ro" "$image" sh /src/infra/install/install.sh
done
```

`pnpm test:install-distros` runs the same three containers, and the `install-script` CI job runs them too. These containers set `OFFGRID_INSTALL_PREREQUISITES_ONLY=1`, which stops the script after the Docker checks so that they do not download a release.

## Backups and restore

The install script does not back up anything. The data lives in the named volumes `offgrid_offgrid-db` (the database), `offgrid_offgrid-files` (uploaded files), `offgrid_offgrid-secrets` (the generated secrets) and `offgrid_offgrid-backups` (the backups that the updater keeps before an update). Keep `offgrid-secrets` together with the database: a restored database needs the secrets that match it.

The complete commands for a manual backup, the database restore, the backups in `offgrid_offgrid-backups`, and the recovery after a failed update are in the [README, Backup and restore](../README.md#backup-and-restore) and [Recovery](../README.md#recovery). The short version:

- Dump the database with `pg_dump --format=custom` from the `db` service, as the `postgres` user.
- Copy `offgrid_offgrid-secrets` and `offgrid_offgrid-files` with a one-off `alpine` container, as shown in the README.
- Restore the dump with `pg_restore` from the `db` service, as `offgrid_migrator`, while the `server` and `web` services are stopped. The restore needs the ownership set by the `db-ownership` service, which runs on a fresh install.

`docker compose down` without `-v` stops the stack and keeps the volumes. `down -v` deletes them, including the data.
