# @offgrid/files

Purpose: file storage and metadata. File bytes live on a disk volume behind a storage port, and the metadata lives in this module's Postgres schema ([ADR 0033](../../docs/adr/0033-file-bytes-on-a-disk-volume.md), [ADR 0034](../../docs/adr/0034-files-access-model-trash-and-versions.md)).
Public API: only what `src/index.ts` exports; never import from `src/` internals.
Owner: module team (files)

## Schema and role

- Schema `files`, runtime role `offgrid_app`, as for every module ([ADR 0009](../../docs/adr/0009-table-ownership-scopes.md)). The module touches no other schema, and the sweep reads no other module's data.
- Tables in schema `files` (migration `20261122000000_files_init`, Prisma models `FilesDrive`, `FilesFile`, `FilesFileVersion`), all scope `family-or-user` ([ADR 0034](../../docs/adr/0034-files-access-model-trash-and-versions.md)):
  - `drive`: one personal drive per user and one family drive per family (partial unique indexes). `kind` is `personal` or `family` and must match the owner. `name` is a stored copy (1 to 255 characters) set when the drive is created (see Drive creation); a later rename needs its own write path.
  - `file`: folders and regular files. A folder has no `mime_type`, `size_bytes` or `current_version_id`; a regular file has both `mime_type` and `size_bytes`. `size_bytes` is `bigint`. Trash is `deleted_at`. Names are unique per parent, case-insensitively, among live rows (`lower(name)`: no Unicode case folding or normalisation).
  - `file_version`: immutable for `offgrid_app` (`UPDATE` revoked; `INSERT` and `DELETE` allowed, the latter for purge). `storage_key` is opaque and never leaves the database or an event.
- Owner consistency is enforced by the database: `owner_id` on each table is generated from the owner columns, and composite foreign keys tie each file to its drive's owner, each version to its file's owner, and each parent folder to the same drive.
- `file.current_version_id` is a deferrable foreign key, so a file, its first version and the pointer commit in one transaction.
- Indexes: `file_children_idx (drive_id, parent_id, name)` for listing, `file_name_per_parent_idx` (unique, live rows only), `file_deleted_at_idx` (partial, trashed rows), `file_version_storage_key_idx`.
- Table `family_membership` (migration `20261202000000_files_family_membership`, Prisma model `FilesFamilyMembership`), scope `family`: a local copy of who is a member of which family, fed by events (see below). Columns `family_id`, `user_id`, `source_version` (at least 1) and `is_member`; primary key `(family_id, user_id)`. A removal stays as a row with `is_member = false`, so a late join cannot revive it. The table holds only ids and a boolean. Its own-rows policy `family_membership_own_rows` lets a user read their own rows. Known limit: `offgrid_app` keeps INSERT, UPDATE and DELETE on this table through the `family` scope grant, because the subscriber runs as `offgrid_app` (ADR 0017: one runtime role) and revoking it would stop projection writes. Only the `files-family-membership` subscriber may write it, by the code rule in `.claude/rules/modules.md`; any other code that writes it is a bug.
- Family membership projection: the subscriber `files-family-membership` (runs as `files`, halts on failure) consumes `family-member-added-v1` and `family-member-removed-v1`. The version check, the event mapping and the subscriber wiring come from `@offgrid/family-projection` (`packages/family-projection`), which calendar uses too. This module supplies only its own table accessor, so the module code has no copy of that logic. Upserts are guarded by `source_version`: a duplicate or stale event is ignored, and a gap on an existing row throws `MembershipChangeOutOfOrderError`, which halts the subscriber. A first event that is not version 1 stores `is_member = false`, so a person whose earlier change predates the projection stays denied. The subscriber cursor starts at 0 and replays history, so existing families are covered.
- Family policies: `drive_family_member_access`, `file_family_member_access` and `file_version_family_member_access` (migration above) allow a user to read and write rows with a `family_id` when `files.is_family_member(family_id)` is true. A non-member or an ex-member sees no rows, so the API answers 404 (the route comes with OG-112). Personal rows stay under the `_scope` policies. The policies add no UPDATE grant, so `offgrid_app` still cannot update `file_version`.
- Helper `files.is_family_member(family_id uuid) returns boolean`: a `LANGUAGE sql STABLE` function that runs with the caller's rights and reads `app.user_id`. It is used only inside the policies, never from application code. It is not `SECURITY DEFINER`, because the own-rows policy already lets the caller see their own membership row, so RLS expresses the access. Calendar inlines the same subquery in its policies instead. Files keeps the helper because one predicate is used by three policies (`drive_family_member_access`, `file_family_member_access`, `file_version_family_member_access`), so the rule lives in one place.
- Accepted lag: a removed member keeps access until the removal event is applied (ADR 0021 and ADR 0034).
- Drive creation: the subscriber `files-personal-drive-from-user-created` consumes `user-created-v1` and creates the person's personal drive, named `Personal`. The subscriber `files-family-drive-from-family-created` consumes `family-created-v1` and creates the family drive, named after the family (the family id comes from the event envelope). Both run as `files` with the default failure policy (retry, then dead letter). Each creates at most one drive per owner: a repeated or replayed event inserts nothing (`createMany` with `skipDuplicates`, covered by the partial unique indexes). `drive-created-v1` is published in the same transaction as the insert, and only when a row was inserted, so a duplicate event publishes nothing. The event carries the drive id and its owner only, never the name.
- Drive backfill: none. Drives exist only for users and families whose creation event this module receives, so the subscribers are the path for new accounts. The outbox keeps events for the retention period (`OFFGRID_OUTBOX_RETENTION_DAYS`, default 7 days), so a replay from an older sequence reaches only retained events. Existing accounts created before this module shipped would need a backfill, which is not provided.

## Storage volume

- The server bind-mounts `data/files` at `/data/files` in Compose. The e2e stack mounts `data/files-e2e` instead.
- The server reads the directory from `OFFGRID_FILES_DIRECTORY` (default `/data/files`) and the upload cap from `OFFGRID_FILES_MAX_UPLOAD_BYTES` (default 50 GiB). See the [server configuration table](../../apps/main-server/README.md#configuration).
- Startup fails, naming the variable, when the directory is missing, is not a directory, or is not writable. `secrets-init` creates the Compose folders with owner 1000:1000 and mode 0700.
- Only this module reads or writes file bytes, through its storage port. The startup check in `apps/main-server/src/lifecycle/probe-directory-writable.ts` creates and removes a probe file in the folder to confirm it is writable.
- Opaque storage keys, not user-chosen names, decide the paths on disk ([ADR 0033](../../docs/adr/0033-file-bytes-on-a-disk-volume.md)).

## Storage port

- Port `FileStorage` in the shared package `@offgrid/file-storage` (`packages/file-storage`, see its README), with five operations: `put(source, { signal? })` returns `{ key, sizeBytes, sha256 }`; `get(key, { start, end? })` returns a stream, with `end` inclusive and optional (omitted means the whole object); `delete(key)` is a no-op for a missing key; `exists(key)` returns a boolean; `listKeys()` yields `{ key, modifiedAt }` for committed objects.
- Keys are 32 lowercase hex characters from 16 random bytes, generated by the server. Every operation rejects a key that does not match `^[0-9a-f]{32}$` with `StorageKeyInvalidError` before it touches disk. The disk adapter also checks that the resolved path stays under the root.
- Adapters: `createDiskFileStorage(directory)` is the one the server uses, and `createInMemoryFileStorage()` is the fake for tests. Both are exported from `@offgrid/file-storage`. The disk layout (`<root>/ab/cd/<key>`, temporary writes, fsync, rename), the errors and the memory budget test are described in the package README.
- Errors carry fixed messages and never a key, path, hash or name. The error classes are the package's, so every adapter throws the same ones.
- Testing: the disk adapter and the fake both run the shared contract suite, `describeFileStorageContract` from `@offgrid/file-storage/testing`.
- Not in this port: a maximum upload size (the upload route, OG-114, owns `maxUploadBytes`), startup cleanup of `.tmp/`, and the S3-compatible adapter.

## Integrity sweep

- `checkStorageIntegrity` reports orphan bytes (a stored key with no `files.file_version` row, older than one hour) and missing bytes (a `files.file_version` row whose key has no bytes). It returns the keys in process and never deletes or repairs anything.
- It reads only this module's own table `files.file_version`, and the storage port. It reads the table in key-ordered batches of 1000, one short transaction per batch, with the policy below. The disk listing is streamed.
- Policy `file_version_storage_sweep_read` (migration `20261201000000_files_storage_sweep`) is a SELECT-only policy on `files.file_version`, keyed on the transaction setting `app.files_storage_sweep`. `withFilesStorageSweepContext` in `packages/db` sets it for the length of one transaction. The policy adds no write access and widens no other table.
- The worker `files-storage-integrity-sweep` runs once, one minute after start, then every 24 hours. It logs counts only (`orphanCount`, `missingCount`, `checkedRowCount`, `checkedObjectCount`) at `info`, and at `warn` when either count is above zero. It never logs a key, path, hash or size.
- Tests: `check-storage-integrity.integration.test.ts` runs on a real Postgres and a real directory, and the migration test is `packages/db/src/files-storage-sweep.integration.test.ts`.

## Contracts

- Will serve the routes in `filesRoutes` from `@offgrid/contracts`: drives, folders, files, trash, versions, downloads and resumable uploads. Path parameters and bodies are validated with the contracts schemas.
- Publishes `drive-created-v1` when a drive is created (see Drive creation above). Will publish `file-created-v1`, `file-updated-v1` and `file-removed-v1` with the payloads defined in `@offgrid/contracts`. The payloads carry ids, owners and versions. Created and updated file events also carry the name. No event carries file contents, storage keys, paths or checksums ([ADR 0033](../../docs/adr/0033-file-bytes-on-a-disk-volume.md), [ADR 0034](../../docs/adr/0034-files-access-model-trash-and-versions.md)).
- The outbox writes, projection consumers, and replay, idempotency and dead-letter tests belong to the issues that publish and consume these events; this package ships only the contract and its payload tests.
