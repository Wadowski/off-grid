# @offgrid/files

Purpose: file storage and metadata. File bytes live on a disk volume behind a storage port, and the metadata lives in this module's Postgres schema ([ADR 0033](../../docs/adr/0033-file-bytes-on-a-disk-volume.md), [ADR 0034](../../docs/adr/0034-files-access-model-trash-and-versions.md)).
Public API: only what `src/index.ts` exports; never import from `src/` internals.
Owner: module team (files)

## Schema and role

- Schema `files`, runtime role `offgrid_app`, as for every module ([ADR 0009](../../docs/adr/0009-table-ownership-scopes.md)). The module touches no other schema, and the sweep reads no other module's data.
- Tables in schema `files` (migration `20261122000000_files_init`, Prisma models `FilesDrive`, `FilesFile`, `FilesFileVersion`), all scope `family-or-user` ([ADR 0034](../../docs/adr/0034-files-access-model-trash-and-versions.md)):
  - `drive`: one personal drive per user and one family drive per family (partial unique indexes). `kind` is `personal` or `family` and must match the owner. `name` is a stored copy (1 to 255 characters) set when the drive is created (see Drive creation); a later rename needs its own write path.
  - `file`: folders and regular files. A folder has no `mime_type`, `size_bytes` or `current_version_id`; a regular file has both `mime_type` and `size_bytes`. `size_bytes` is `bigint`. Trash is `deleted_at`. Names are unique per parent, case-insensitively, among live rows (`lower(name)`: no Unicode case folding or normalisation).
  - `file_version`: immutable for `offgrid_app` (`UPDATE` revoked; `INSERT` and `DELETE` allowed, the latter for purge and for deleting a non-current version, see File versions API). `storage_key` is opaque and never leaves the database or an event.
- Owner consistency is enforced by the database: `owner_id` on each table is generated from the owner columns, and composite foreign keys tie each file to its drive's owner, each version to its file's owner, and each parent folder to the same drive.
- `file.current_version_id` is a deferrable foreign key, so a file, its first version and the pointer commit in one transaction.
- Indexes: `file_children_idx (drive_id, parent_id, name)` for listing, `file_name_per_parent_idx` (unique, live rows only), `file_deleted_at_idx` (partial, trashed rows), `file_version_storage_key_idx`.
- Table `family_membership` (migration `20261202000000_files_family_membership`, Prisma model `FilesFamilyMembership`), scope `family`: a local copy of who is a member of which family, fed by events (see below). Columns `family_id`, `user_id`, `source_version` (at least 1) and `is_member`; primary key `(family_id, user_id)`. A removal stays as a row with `is_member = false`, so a late join cannot revive it. The table holds only ids and a boolean. Its own-rows policy `family_membership_own_rows` lets a user read their own rows. Known limit: `offgrid_app` keeps INSERT, UPDATE and DELETE on this table through the `family` scope grant, because the subscriber runs as `offgrid_app` (ADR 0017: one runtime role) and revoking it would stop projection writes. Only the `files-family-membership` subscriber may write it, by the code rule in `.claude/rules/modules.md`; any other code that writes it is a bug.
- Family membership projection: the subscriber `files-family-membership` (runs as `files`, halts on failure) consumes `family-member-added-v1` and `family-member-removed-v1`. The version check, the event mapping and the subscriber wiring come from `@offgrid/family-projection` (`packages/family-projection`), which calendar uses too. This module supplies only its own table accessor, so the module code has no copy of that logic. Upserts are guarded by `source_version`: a duplicate or stale event is ignored, and a gap on an existing row throws `MembershipChangeOutOfOrderError`, which halts the subscriber. A first event that is not version 1 stores `is_member = false`, so a person whose earlier change predates the projection stays denied. The subscriber cursor starts at 0 and replays history, so existing families are covered.
- Family policies: `drive_family_member_access`, `file_family_member_access` and `file_version_family_member_access` (migration above) allow a user to read and write rows with a `family_id` when `files.is_family_member(family_id)` is true. A non-member or an ex-member sees no rows, so the API answers 404. Personal rows stay under the `_scope` policies. The policies add no UPDATE grant, so `offgrid_app` still cannot update `file_version`.
- Helper `files.is_family_member(family_id uuid) returns boolean`: a `LANGUAGE sql STABLE` function that runs with the caller's rights and reads `app.user_id`. It is used only inside the policies, never from application code. It is not `SECURITY DEFINER`, because the own-rows policy already lets the caller see their own membership row, so RLS expresses the access. Calendar inlines the same subquery in its policies instead. Files keeps the helper because one predicate is used by three policies (`drive_family_member_access`, `file_family_member_access`, `file_version_family_member_access`), so the rule lives in one place.
- Accepted lag: a removed member keeps access until the removal event is applied (ADR 0021 and ADR 0034).
- Drive creation: the subscriber `files-personal-drive-from-user-created` consumes `user-created-v1` and creates the person's personal drive, named `Personal`. The subscriber `files-family-drive-from-family-created` consumes `family-created-v1` and creates the family drive, named after the family (the family id comes from the event envelope). Both run as `files` with the default failure policy (retry, then dead letter). Each creates at most one drive per owner: a repeated or replayed event inserts nothing (`createMany` with `skipDuplicates`, covered by the partial unique indexes). `drive-created-v1` is published in the same transaction as the insert, and only when a row was inserted, so a duplicate event publishes nothing. The event carries the drive id and its owner only, never the name.
- Drive backfill: none. Drives exist only for users and families whose creation event this module receives, so the subscribers are the path for new accounts. The outbox keeps events for the retention period (`OFFGRID_OUTBOX_RETENTION_DAYS`, default 7 days), so a replay from an older sequence reaches only retained events. Existing accounts created before this module shipped would need a backfill, which is not provided.

## Storage volume

- The server bind-mounts `data/files` at `/data/files` in Compose. The e2e stack mounts `data/files-e2e` instead.
- The server reads the directory from `OFFGRID_FILES_DIRECTORY` (default `/data/files`) and the upload cap from `OFFGRID_FILES_MAX_UPLOAD_BYTES` (default 50 GiB). See the [server configuration table](../../apps/main-server/README.md#configuration).
- Startup fails, naming the variable, when the directory is missing, is not a directory, or is not writable. `secrets-init` creates the Compose folders with owner 1000:1000 and mode 0700.
- Only this module reads or writes file bytes, through its storage port. The startup check in `apps/main-server/src/lifecycle/probe-directory-writable.ts` creates and removes a probe file in the folder to confirm it is writable.
- Opaque storage keys, not user-chosen names, decide the paths on disk ([ADR 0033](../../docs/adr/0033-file-bytes-on-a-disk-volume.md)).

## Storage port

- Port `FileStorage` in the shared package `@offgrid/file-storage` (`packages/file-storage`, see its README), with five operations: `put(source, { signal? })` returns `{ key, sizeBytes, sha256 }`; `get(key, { start, end? })` returns a stream, with `end` inclusive and optional (omitted means the whole object); `delete(key)` is a no-op for a missing key; `exists(key)` returns a boolean; `listKeys()` yields `{ key, modifiedAt }` for committed objects.
- Keys are 32 lowercase hex characters from 16 random bytes, generated by the server. Every operation rejects a key that does not match `^[0-9a-f]{32}$` with `StorageKeyInvalidError` before it touches disk. The disk adapter also checks that the resolved path stays under the root.
- Adapters: `createDiskFileStorage(directory)` is the one the server uses, and `createInMemoryFileStorage()` is the fake for tests. Both are exported from `@offgrid/file-storage`. The disk layout (`<root>/ab/cd/<key>`, temporary writes, fsync, rename), the errors and the memory budget test are described in the package README.
- Errors carry fixed messages and never a key, path, hash or name. The error classes are the package's, so every adapter throws the same ones.
- Testing: the disk adapter and the fake both run the shared contract suite, `describeFileStorageContract` from `@offgrid/file-storage/testing`.
- Not in this port: startup cleanup of `.tmp/`, and the S3-compatible adapter. The upload size limit is applied by the upload route, not by the port.

## Integrity sweep

- `checkStorageIntegrity` reports orphan bytes (a stored key with no `files.file_version` row, older than one hour) and missing bytes (a `files.file_version` row whose key has no bytes). It returns the keys in process and never deletes or repairs anything.
- It reads only this module's own table `files.file_version`, and the storage port. It reads the table in key-ordered batches of 1000, one short transaction per batch, with the policy below. The disk listing is streamed.
- Policy `file_version_storage_sweep_read` (migration `20261201000000_files_storage_sweep`) is a SELECT-only policy on `files.file_version`, keyed on the transaction setting `app.files_storage_sweep`. `withFilesStorageSweepContext` in `packages/db` sets it for the length of one transaction. The policy adds no write access and widens no other table.
- The worker `files-storage-integrity-sweep` runs once, one minute after start, then every 24 hours. It logs counts only (`orphanCount`, `missingCount`, `checkedRowCount`, `checkedObjectCount`) at `info`, and at `warn` when either count is above zero. It never logs a key, path, hash or size.
- Tests: `check-storage-integrity.integration.test.ts` runs on a real Postgres and a real directory, and the migration test is `packages/db/src/files-storage-sweep.integration.test.ts`.

## Browse API

- Routes (mounted under `/api` by the server): `GET /drives` lists the caller's personal drive and the family drives of the families they are in. `GET /drives/:id/children` lists the root of a drive. `GET /files/:id` returns a file or folder with its breadcrumbs. `GET /files/:id/children` lists the inside of a folder with its breadcrumbs. Each folder in a children list carries `itemCount`, the number of its live direct children (not recursive, computed at read time with one grouped count per page); other file responses have no `itemCount`. Path parameters and the `cursor`, `limit`, `sort` and `direction` query are validated with the contracts schemas. A malformed cursor, or a cursor made for another `sort` or `direction`, answers 400 `VALIDATION_FAILED`.
- Visibility is RLS only. Every read runs in a transaction that sets the user context (`withUserContext`). A drive, folder or file that the caller cannot see, including a file in another family's drive, a former member's family drive, a trashed entry and an entry inside a trashed folder, answers 404. Never 403.
- Trash: every query filters `deleted_at is null`. A trashed folder is not walked, so its children are not reachable.
- Paging: an opaque cursor (base64url of the last row's `isFolder`, `fileId`, `sort`, `direction` and the sort value of that row) with the default limit 50 and maximum 200. The query fetches `limit + 1` rows to know whether a next page exists, so `nextCursor` is `null` on the last page. A cursor without `sort` is read as name ascending.
- Order: folders first, then the `sort` field (`name` by default, `modified` for `updatedAt`, `size` for `sizeBytes`) in the `direction` (`asc` by default), then by file id. Folders have no size, so under `size` they are ordered by name. Names are ordered by the database collation, not by case-insensitive or Unicode order. The modified and size keysets compare the stored values, so `updatedAt` must be stored with millisecond precision, as Prisma writes it. The cursor compares with the same order, so paging stays consistent. Trash keeps the name order.
- Breadcrumbs always start with the drive (`kind: "drive"`). A drive listing has only the drive crumb. A folder listing has the drive and then each folder from the root down to and including the listed folder. File details have the drive and then the ancestors, without the file itself.
- The ancestor walk reads one parent per query and stops at 256 levels, answering 404 when a parent is missing, trashed or invisible.
- Responses never include bytes, `storage_key`, checksums or versions beyond `version` and `currentVersionId`. Regular file sizes are numbers, and a size above the safe integer range fails the response.
- Not in this route set yet: the `/uploads` routes for chunked and resumable uploads, and the `parent` parameter.

## Organising API

- `POST /drives/:id/folders` creates a folder at the drive root (`parentId` null) or inside a live folder of the drive. It answers 201 with the folder and publishes `file-created-v1`.
- `PATCH /files/:id` renames a file or folder. It answers 200 with the entry, bumps `version` and publishes `file-updated-v1`. A rename to the same name changes nothing: no bump and no event.
- `POST /files/:id/move` moves an entry to a folder or to the root of a drive. It answers 200 with `{ file, crossOwnerNotice }` and publishes one event per changed row.
  - Inside one drive, the row keeps its id. It bumps `version`, publishes `file-updated-v1`, and `crossOwnerNotice` is false. A move to the current place changes nothing.
  - To a drive of another owner, the subtree is copied. Each entry gets a new id, version 1, and each regular file gets its current version copied to new storage. The source rows are removed, and each source entry publishes `file-removed-v1`. Each copy publishes `file-created-v1`. `crossOwnerNotice` is true. The copy and the removal are one transaction. The source bytes are deleted after the commit. If the copy fails, the copied bytes are deleted on a best-effort basis. See [ADR 0037](../../docs/adr/0037-cross-owner-move-copy-and-removal.md).
- A name is refused with 409 `NAME_TAKEN` when a live sibling has it, ignoring case. A race on the unique index gives the same answer.
- A folder cannot move into itself or into its own subtree, and a subtree above `MAX_MOVE_ENTRY_COUNT` entries cannot move across owners. Both answer 409 `INVALID_MOVE`.
- A target folder that is missing, trashed, a regular file, or in another drive answers 404, and so does a target drive the caller cannot see. The drive is checked first.
- Names and storage keys: event payloads carry names, ids and versions, as [ADR 0034](../../docs/adr/0034-files-access-model-trash-and-versions.md) section 9 allows. Storage keys, paths and checksums never leave the database or the storage port, and logs never carry names.

## Upload API

- `POST /drives/:id/files` stores a new regular file at the root of a drive or inside a live folder of the drive. The body is the file bytes as they are; there is no multipart wrapper ([ADR 0038](../../docs/adr/0038-streamed-upload-request-shape.md)).
- Headers: `X-Offgrid-File-Name` is required and carries the percent-encoded name, validated with `fileNameSchema` after decoding (a malformed encoding is 400). `X-Offgrid-Parent-Id` is optional; absent means the drive root. `Content-Type` is the declared media type, validated and stripped of parameters; without it the type comes from the name extension (a small built-in map), then `application/octet-stream`. No bytes are sniffed.
- The raw body parser is registered in an encapsulated Fastify scope for this route only, so the JSON routes keep their parsing.
- Answers 201 with the `File` schema, with `version` 1. An empty body is an empty file. Errors: 400 `VALIDATION_FAILED`, 401, 404 `NOT_FOUND` for a drive or parent the caller cannot see (including a parent in another drive, a file, or a trashed folder), 409 `NAME_TAKEN` for a live sibling with the same name (ignoring case), and 413 `PAYLOAD_TOO_LARGE` above `OFFGRID_FILES_MAX_UPLOAD_BYTES`.
- Name conflicts answer 409 and are not renamed with a suffix. This follows the rule in [ADR 0034](../../docs/adr/0034-files-access-model-trash-and-versions.md): every create path refuses collisions.
- Size: a `Content-Length` above the limit is refused before the body is read. For a body without a length, the stream wrapper counts bytes as they arrive and stops at the first byte past the limit. The storage write is aborted, its temporary file is removed, and the connection is closed after the 413.
- Order of operations: (a) a read transaction as the caller checks the drive, the parent and the name, so a non-member or a taken name never writes bytes; (b) `storage.put` streams the limited body to the storage port; (c) one write transaction re-checks the drive, the parent and the name, inserts the file and its first version (number 1, storage key, size, mime type, SHA-256, creator) and publishes `file-created-v1`; (d) if (b) succeeded and (c) fails or finds the entry gone, the stored bytes are deleted. A concurrent create of the same name fails the unique index and gives 409, and its bytes are deleted the same way.
- A crash between (b) and (c) leaves orphan bytes. The storage integrity sweep reports them ([Integrity sweep](#integrity-sweep)); nothing deletes them automatically.
- The event carries the file id, drive, owner, name, mime type, size and version, never the storage key, path or checksum.
- Tests: the stream limiter and the mime resolver are unit tested in `domain/files`; `upload-file.integration.test.ts` covers the application flow against real Postgres; `register-upload-file.integration.test.ts` covers the route; `test/upload-memory-budget.integration.test.ts` streams 512 MiB through the disk adapter and asserts the heap growth stays under 64 MiB.

## Download API

- `GET /files/:id/content` sends the bytes of the current version, and `GET /files/:id/versions/:versionId/content` sends the bytes of one version. Both answer 200 with the whole body, or 206 for a byte range. The version route answers 404 for a version of another file.
- A `Range` header is honoured only in its single-range forms `bytes=a-b`, `bytes=a-` and `bytes=-n`. A malformed header, another unit or several ranges are ignored and the whole file is sent. A range outside the file answers 416 `RANGE_NOT_SATISFIABLE` with `Content-Range: bytes */size`.
- The query `disposition` is `attachment` by default. `inline` is honoured only for `image/png`, `image/jpeg`, `image/gif`, `image/webp` and `application/pdf`. Every other type is an attachment sent as `application/octet-stream`, so a stored HTML or SVG file is never rendered. An inline image is sent with `Content-Security-Policy: default-src 'none'; sandbox`, and an inline PDF with the viewer policy. See [ADR 0040](../../docs/adr/0040-safe-headers-and-inline-preview-for-file-content.md).
- Every success carries `Content-Length`, `Content-Type`, `Content-Disposition` (an ASCII `filename` and an RFC 5987 `filename*`), `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store` and `Accept-Ranges: bytes`.
- Answers 400 `IS_FOLDER` for a folder, 400 `VALIDATION_FAILED` for a bad id, query or disposition, 401, and 404 for a file or version the caller cannot see (hidden, trashed, unknown) or whose bytes are missing from storage. The bytes are streamed after the database transaction closes. Names, storage keys and checksums are never logged.

## File versions API

- `GET /files/:id/versions` lists the versions of a regular file, newest first (number descending), as `FileVersionList`. Each version has `id`, `fileId`, `number`, `size`, `mimeType`, `createdByUserId` and `createdAt`. Answers 200, 400 `IS_FOLDER` for a folder, 401, and 404 for a file the caller cannot see (hidden, trashed, unknown).
- `POST /files/:id/versions` uploads a new version of a regular file. The body is the raw bytes. The optional `Content-Type` is the media type of the new version; without it the file keeps its current media type. There is no name header. It adds a version numbered one above the highest number, makes it current, updates the file's `size` and `mimeType`, bumps `version` and publishes `file-updated-v1`. Older versions stay. Answers 201 with the `File`. Errors: 400 `IS_FOLDER`, 401, 404, and 413 `PAYLOAD_TOO_LARGE` above `OFFGRID_FILES_MAX_UPLOAD_BYTES`. A `Content-Length` above the limit is refused before the body is read. Nothing is stored on any error.
- `POST /files/:id/versions/:versionId/restore` makes an older version current. The bytes are copied to a new storage key, and a new version (number one above the highest) refers to the copy. The old row is not changed. It publishes `file-updated-v1`. Restoring the current version answers 200 with the file unchanged and publishes nothing. See [ADR 0039](../../docs/adr/0039-delete-non-current-version-and-restore-copies-bytes.md).
- `DELETE /files/:id/versions/:versionId` removes a version that is not current. Its row is deleted, and its bytes are deleted after the commit. It answers 204 and publishes no event. Deleting the current version answers 409 `CURRENT_VERSION` and removes nothing. Hidden, trashed, unknown and other-file ids answer 404, never 403.
- Order of operations for an upload: (a) a read transaction checks that the file is live, visible and not a folder, so a hidden file never writes bytes; (b) `storeLimitedUpload` streams the limited body to the storage port; (c) one write transaction locks the file row, re-checks it, computes the next number, inserts the version, updates the file and publishes the event; (d) if (b) succeeded and (c) fails or finds the file gone, the stored bytes are deleted. Concurrent uploads to one file serialise on the file row, so they get distinct numbers.
- Order of operations for a restore: a read transaction finds the source version; the bytes are copied outside a transaction; one write transaction re-checks the source and appends the copy as a new version; if the copy or the write fails, the copied bytes are deleted.
- Version responses never carry `storage_key`, `sha256` or the storage path. Downloads of a version are described in the Download API section.

## Contracts

- Serves the browse, organising, upload, file versions and download routes above from `filesRoutes` in `@offgrid/contracts`. The rest of `filesRoutes` (trash and resumable uploads) comes with its issues.
- Publishes `drive-created-v1` when a drive is created (see Drive creation above), and `file-created-v1`, `file-updated-v1` and `file-removed-v1` for the organising routes, with the payloads defined in `@offgrid/contracts`. The payloads carry ids, owners and versions. Created and updated file events also carry the name. No event carries file contents, storage keys, paths or checksums ([ADR 0033](../../docs/adr/0033-file-bytes-on-a-disk-volume.md), [ADR 0034](../../docs/adr/0034-files-access-model-trash-and-versions.md)).
- The outbox writes for these events are in the same transaction as the change they describe. Projection consumers of these events, and their replay, idempotency and dead-letter tests, belong to the issues that consume them.

## Trash, restore and purge

- `POST /files/:id/trash` sets `deleted_at` on that row only and publishes one `file-updated-v1` with `deletedAt`. Descendants are hidden by the live-ancestor checks, so they are not marked.
- `GET /drives/:id/trash` lists trashed rows of a drive (folders first, then name, then id), paged like the children list. The trash takes only `cursor` and `limit`: `sort` and `direction` are not trash parameters, and any unknown query parameter, including them, answers 400 `VALIDATION_FAILED`. A cursor from another order (for example a size cursor) also answers 400. `DELETE /drives/:id/trash` empties it.
- `POST /files/:id/restore` clears `deleted_at` and returns the row to its original parent when that parent and its whole chain are live, else to the drive root. A live sibling with the same name gives a `(n)` suffix. A live row answers 409 `NOT_TRASHED`.
- `DELETE /files/:id` purges a trashed row and its subtree: rows, versions and bytes, in one transaction that holds the trashed chain lock and deletes in chunks of 500 rows, deepest first, with one `file-removed-v1` per row at `version + 1`. A restore of a row under a trashed root waits for the purge. A live row answers 409 `NOT_TRASHED`.
- The retention worker `files-trash-purge` runs two minutes after start and every 24 hours. It purges trashed roots older than `OFFGRID_FILES_TRASH_RETENTION_DAYS` as the owner, or as a current member for a family drive. A family drive with no current member is skipped and counted (`skippedRootCount`). It logs counts only.
- The worker reads through the read-only policies `file_trash_purge_read` and `family_membership_trash_purge_read`, set by `withFilesTrashPurgeContext`. It has no write access of its own. See [ADR 0041](../../docs/adr/0041-files-trash-purge-worker.md).
